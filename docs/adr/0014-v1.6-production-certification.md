# ADR 0014: Better Auth 1.6 production certification

- Status: Accepted
- Date: 2026-07-28
- Better Auth oracle: `better-auth@1.6.25`
- Migration baseline: commit `ecf48ac` (`feat: add core management and SQL adapters`)

## Context

The Go server already implements the principal Better Auth 1.6 core, plugin,
database, and HTTP contracts. Three release-blocking areas remain:

1. email/password and email-verification lifecycle options, including both
   change-email modes;
2. release-to-release database upgrade evidence for SQLite, PostgreSQL, and
   MongoDB; and
3. deterministic certification of every Better Auth 1.6.25 social-provider
   preset and the generic OAuth/OIDC provider API.

The TypeScript package is an interoperability oracle, not a runtime dependency.
The Go library continues to own its cryptography, persistence, HTTP handlers,
and security boundaries.

## Decision

### Email lifecycle

Add an `EmailVerificationConfig` and typed lifecycle hooks for:

- `sendOnSignUp`, preserving the upstream tri-state default that follows
  `requireEmailVerification`;
- `sendOnSignIn`;
- `autoSignInAfterVerification`;
- before/after email-verification callbacks;
- `onPasswordReset`; and
- enumeration-safe `onExistingUserSignUp`; and
- `customSyntheticUser` response shaping for application-defined public
  fields.

Change-email supports the two Better Auth 1.6 modes:

- an unverified current address may be replaced immediately only when
  `updateEmailWithoutVerification` is enabled; and
- a verified current address may require confirmation at the old inbox before
  the verification message is delivered to the new inbox.

All tokens remain opaque, hashed at rest, expiring, and single use. Callback
targets remain restricted to configured origins. Hook failures never weaken
the single-use guarantee: a consumed token remains consumed.

### Database upgrades

The project does not yet have semantic release tags, so commit `ecf48ac` is the
first frozen adapter baseline. Each first-party adapter receives an upgrade
fixture that:

- migrates or initializes the frozen baseline;
- seeds representative core data;
- applies the current schema more than once;
- proves data remains readable and constraints/indexes are present; and
- proves current authentication storage operations work after the upgrade.

Future releases add fixtures rather than rewriting this baseline.

### Provider certification

The provider catalog is fixed to the 35 presets exported by Better Auth
1.6.25:

`apple`, `atlassian`, `cognito`, `discord`, `dropbox`, `facebook`, `figma`,
`github`, `gitlab`, `google`, `huggingface`, `kakao`, `kick`, `line`, `linear`,
`linkedin`, `microsoft`, `naver`, `notion`, `paybin`, `paypal`, `polar`,
`railway`, `reddit`, `roblox`, `salesforce`, `slack`, `spotify`, `tiktok`,
`twitch`, `twitter`, `vercel`, `vk`, `wechat`, and `zoom`.

Certification is table-driven and deterministic. It covers catalog identity,
authorization endpoints and parameters, default scopes, PKCE, token request
authentication, bounded response handling, representative provider profile
mapping, and provider-error sanitization.

The generic API supports both explicitly configured OAuth 2.0 providers and
OIDC discovery. OIDC discovery and JWKS fetching use bounded clients, reject
redirects, validate endpoints and issuer identity, verify `RS256` ID tokens,
and use an injectable clock. Application-supplied explicit endpoints remain a
trusted configuration boundary.

## Implementation plan

1. Add lifecycle configuration, hooks, change-email state transitions, and
   black-box failure/replay tests.
2. Add frozen upgrade fixtures to the SQLite, PostgreSQL, and MongoDB adapter
   suites.
3. Add provider-aware profile mapping, a generic OIDC constructor, and the
   35-preset/generic-provider certification matrix.
4. Update compatibility and progress documentation.
5. Run formatting, unit, black-box, adapter, race, fuzz-smoke, vet, static, and
   vulnerability checks before merging.

## Consequences

The new options are opt-in and preserve existing secure defaults. The public
API grows only where Better Auth 1.6 exposes a corresponding contract.
Certification is intentionally limited to Better Auth 1.6.25; later provider
or plugin behavior requires a separate versioned compatibility decision.
