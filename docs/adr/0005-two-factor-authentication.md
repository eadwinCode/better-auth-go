# ADR 0005: Two-factor authentication security contract

- Status: Accepted
- Date: 2026-07-28
- Scope: isolated `plugin/twofactor` pull request

## Context

Better Auth v1.6 exposes a two-factor plugin covering TOTP enrollment and
verification, delivered one-time passwords, backup codes, trusted devices, and
credential-sign-in interception. The Go library must preserve those HTTP
contracts without allowing a first-factor session to escape before the second
factor succeeds.

The plugin is independent from passkeys, organizations, SSO, and SCIM. Those
features may consume the same plugin kernel later, but are not dependencies of
this ADR.

## Decision

### Public HTTP contract

The plugin contributes these Better Auth-shaped endpoints:

- `POST /two-factor/enable`
- `POST /two-factor/disable`
- `POST /two-factor/get-totp-uri`
- `POST /two-factor/verify-totp`
- `POST /two-factor/send-otp`
- `POST /two-factor/verify-otp`
- `POST /two-factor/generate-backup-codes`
- `POST /two-factor/verify-backup-code`

Viewing backup codes remains a server-only `Manager` operation and is never
mounted as an HTTP endpoint.

The credential sign-in response is replaced with:

```json
{
  "twoFactorRedirect": true,
  "twoFactorMethods": ["totp", "otp"]
}
```

when the user has enabled 2FA and the request does not present a valid trusted
device. The provisional first-factor session is revoked before that response is
committed.

### Secrets and bearer values

- Applications must inject a `TokenCipher`; startup fails closed without it.
- TOTP secrets and the recoverable backup-code set are encrypted at rest.
- Pending-login, delivered-OTP, and trusted-device cookies contain opaque random
  values. Only SHA-256 hashes are persisted.
- Cookies are host-only, `__Host-` prefixed, `Secure`, `HttpOnly`, `Path=/`, and
  use the server SameSite policy.
- TOTP uses RFC 6238 with six or eight digits, a bounded period, and a
  one-period clock-skew window.
- Backup codes are cryptographically random, normalized before comparison,
  consumed with an expected-old-value guard, and never logged.

### Enrollment and management

- Enrollment, secret retrieval, disabling, and backup-code regeneration require
  an authenticated fresh session, trusted origin, and CSRF validation.
- A password is required whenever the user has a credential account.
  `AllowPasswordless` only permits management without a password when no
  credential account exists.
- `twoFactorEnabled` remains false until the newly generated TOTP secret is
  verified, unless the explicitly unsafe-compatible
  `SkipVerificationOnEnable` option is enabled.
- Enabling, disabling, and backup-code regeneration rotate the browser session.
- Re-enrollment replaces the previous secret and backup-code set atomically.

### Sign-in verification

- The pending-login challenge is single-use, expires after a bounded interval,
  and is bound to one user.
- A separate consume-and-rearm attempt record serializes concurrent guesses.
  Server failures restore the attempt; invalid factors spend it.
- TOTP, delivered OTP, and backup codes share both the per-challenge budget and
  the durable per-account consecutive-failure counter.
- Exceeding the challenge budget destroys the pending login. Exceeding the
  account budget sets a bounded lockout. A successful sign-in verification
  clears the account counter.
- The pending challenge is atomically consumed before session issuance.
- Trusted-device records are server-side, user-bound, expiring, revocable, and
  rotated whenever accepted.

### OTP delivery

Delivered OTP is opt-in through an injected concurrency-safe callback. The code
is generated by the library and passed to the callback with a public-safe user
value. Delivery failures do not leave a usable OTP record. Re-sending replaces
the previous code for the pending login.

### Schema and adapter behavior

The plugin extends `user` with `twoFactorEnabled` and contributes a
`twoFactor` model containing the encrypted material, verification state,
failure counter, lockout deadline, and timestamps. `userId` is unique so every
user has at most one active 2FA configuration.

The existing verification model stores expiring pending-login, attempt, OTP,
and trusted-device records. MongoDB and SQL migrations derive the necessary
indexes from the merged schema.

### Auditability

Enrollment completion, disabling, backup-code regeneration and consumption,
account lockout, trusted-device creation, and successful second-factor sign-in
produce durable audit events. Audit records contain factor type and bounded
request metadata, never codes, secrets, cookie values, or hashes.

## Compatibility notes

The HTTP paths and primary request/response shapes follow Better Auth v1.6.
Native Go security defaults are deliberately stricter:

- encrypted secret material is mandatory rather than optional;
- backup codes cannot be stored in plaintext;
- server-only backup-code viewing cannot be exposed accidentally over HTTP;
- sensitive management operations require a fresh session and CSRF token;
- all pending and trusted-device bearer values are opaque and hash-only at rest.

The core currently supports email/password credential sign-in, so interception
is applied to `/sign-in/email`. Future credential providers must opt into the
same post-first-factor transition before claiming 2FA parity.

## Verification plan

- black-box enable, enrollment verification, sign-in challenge, TOTP, OTP,
  backup-code, trusted-device, disable, and regeneration tests;
- deterministic RFC 6238 vectors and clock-boundary tests;
- concurrent challenge and backup-code consumption tests;
- adapter migration/index tests for SQLite, PostgreSQL, and MongoDB;
- security failures for stale sessions, CSRF/origin rejection, expired and
  replayed challenges, wrong-user cookies, delivery failures, attempt caps,
  account lockout, corrupt ciphertext, and session fixation;
- fuzz tests for pending-login and trusted-device cookie parsing;
- `go test`, `go vet`, race detector, static analysis, and vulnerability scan.
